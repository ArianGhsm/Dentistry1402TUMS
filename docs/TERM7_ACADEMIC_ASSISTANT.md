# دستیار برنامه ترم ۷

منبع برنامه، `public_html/api/academic_term7.php` و نسخهٔ فعلی آن
`1405-1406.5` است. عضویت گروه‌ها داخل کد یا PDF حدس زده نمی‌شود و فقط با شماره
دانشجویی canonical در storage خصوصی `academic/term7-1405-1406.json` نگه‌داری
می‌شود. این فایل بخشی از دادهٔ پایدار سرور است و با deploy جایگزین نمی‌شود.

## مدل canonical گروه‌ها

دو assignment مستقل برای هر دانشجو نگه‌داری می‌شود:

- `group10`: گروه صبح، فقط ۱ تا ۱۰.
- `group8`: گروه عصر، فقط ۱۱ تا ۱۸.

وضعیت هر دانشجو در هر گروه یکی از `leader`، `member` یا `unassigned` است و در UI
با «سرگروه»، «عضو» و «بدون گروه» نمایش داده می‌شود. این وضعیت فقط وضعیت
گروه‌بندی ترم ۷ است و نقش/وضعیت حساب کاربری سایت را تغییر نمی‌دهد.

عضویت گروه در همان state اصلی Term 7 می‌ماند. metadata مدیریتی سرگروه‌ها در
storage خصوصی deploy-safe `academic/term7-1405-1406-leaders.json` نگه‌داری
می‌شود؛ این فایل roster یا membership موازی نیست و فقط برای هر گروه، شماره
دانشجویی canonical سرگروه را ثبت می‌کند. در read، هر اشارهٔ سرگروهی که دیگر با
assignment فعلی همان دانشجو سازگار نباشد نادیده گرفته می‌شود. برای هر گروه
حداکثر یک سرگروه وجود دارد و display name یا شناسهٔ Telegram/Bale مرجع نیست.

مالک از «امور کلاس» ربات می‌تواند گروه صبح، گروه عصر و وضعیت سرگروهی هر دانشجو
را تغییر دهد. mutation گروه فقط `academic/term7-1405-1406.json` را تغییر می‌دهد
و mutation سرگروه فقط metadata مدیریتی بالا را. برنامهٔ شخصی، خلاصه‌های
فردا/هفته و reminderهای ترم ۷ همچنان از assignment canonical اصلی می‌خوانند.

فهرست مدیریتی ربات فقط accountهای cohort `dentistry-1402` را نشان می‌دهد که در
state canonical ترم ۷ assignment صریح دارند. صرفِ وجود یک account در cohort،
آن شخص را عضو فهرست ترم ۷ نمی‌کند. این قاعده اجازه می‌دهد account/link مستقل
بدون تخریب هویت از فهرست ترم ۷ کنار گذاشته شود.

`dent_rotation_group_catalog()` و تطبیق نامی قدیمی `dent_user_rotation_assignment()`
مرجع canonical گروه‌بندی ترم ۷ نیستند و نباید برای ClassOps audience، برنامهٔ
شخصی یا mutation گروه‌های این ترم استفاده شوند.

ایموجی و wording دکمه‌های مدیریت صرفاً presentation هستند و می‌توانند بعداً بدون
تغییر identifierها، storage schema یا قراردادهای business عوض شوند.

## ورود گروه‌ها

ورودی CSV باید header زیر را داشته باشد:

```csv
studentNumber,name,group
40211272000,نام دانشجو,6
```

JSON نیز آرایه‌ای با همین سه field است. شماره دانشجویی مرجع اصلی است. تطبیق نام
فقط fallback است و حروف `ي/ی`، `ك/ک`، نیم‌فاصله و فاصله‌های اضافی را normalize
می‌کند. گزارش dry-run شامل matched، unmatched، ambiguous، duplicate، invalid،
`missingGroup10` و `missingGroup8` است. تا وقتی خطای مبهم/نامعتبر یا کمبود در
فهرست target وجود داشته باشد `--commit` چیزی ثبت نمی‌کند.

ابتدا dry-run و سپس commit گروه‌های ۱ تا ۱۰:

```bash
php scripts/import_term7_groups.php --field=group10 --file=/absolute/group10.csv
php scripts/import_term7_groups.php --field=group10 --file=/absolute/group10.csv --commit
```

برای گروه‌های ۱۱ تا ۱۸:

```bash
php scripts/import_term7_groups.php --field=group8 --file=/absolute/group8.csv
php scripts/import_term7_groups.php --field=group8 --file=/absolute/group8.csv --commit
```

برنامه نظری در نبود گروه هم نمایش داده می‌شود؛ برنامه عملی هرگز حدس زده نمی‌شود.

## طرح درس و عنوان جلسه‌های ترم ۷

روز/روتیشن و occurrence اصلی همچنان فقط در `dent_term7_schedule()` تعریف می‌شود و طرح درس
هیچ timetable موازی نمی‌سازد. برای **ساعت برگزاری** استثنا صریح داریم: ساعت ثبت‌شده
در طرح درس بر ساعت fallback برنامه اولویت دارد؛ اگر طرح درس ساعت معتبری نداشته باشد،
همان ساعت canonical/fallback حفظ می‌شود. timing منبع در resolver مشترک ترم ۷ نیز اعمال
می‌شود تا امور کلاس، خلاصهٔ برنامه و reminderها ساعت واحدی داشته باشند. فایل
`public_html/api/classops_term7_syllabus.php` registry مشترک طرح درس‌ها را روی occurrence
موجود در ClassOps enrich می‌کند و دادهٔ ساخت‌یافتهٔ PDFهای اصلاح‌شده در
`classops_term7_syllabus_data.php` قرار دارد.

registry فعلی این نه درس را پوشش می‌دهد: ارتودنسی نظری ۱، اندودانتیکس نظری ۱،
دندانپزشکی تشخیصی ۳، روش تحقیق ۲، مبانی اندودانتیکس ۲، سلامت دهان عملی ۲،
سلامت دهان نظری ۲، پریو نظری ۱ و مبانی پارسیل نظری. برای هر occurrence فقط metadata لازم مانند
شماره/شماره‌های جلسه، عنوان جلسه، استاد، رفرنس و شیوهٔ برگزاری افزوده می‌شود.
چند جلسهٔ ثبت‌شده در یک تاریخ با شناسهٔ مستقل حفظ می‌شوند و merge نمی‌شوند.

جلسهٔ مجازی یا آفلاین برچسب فارسی صریح دارد. اگر خود طرح درس ساعت صریح دوره/جلسه
را ثبت کرده باشد، همان ساعت حتی برای جلسهٔ مجازی نمایش داده می‌شود؛ اگر ستون ساعت
منبع صریحاً خالی یا `-` باشد، ساعت ساخته نمی‌شود و مکان فیزیکی نیز برای جلسهٔ مجازی
نمایش داده نمی‌شود.
حالت‌هایی مانند «حضوری + کوییز کلاسی»، «کلاس وارونه» و «در صورت برگزاری مجازی»
نیز به‌عنوان metadata جلسه نگه‌داری می‌شوند و recurrence اصلی را تغییر نمی‌دهند.

برای مبانی پارسیل، تاریخ جلسهٔ ۳ در منبع به‌صورت `054/07/15` آمده و به‌دلیل
ابهام تا اصلاح صریح منبع به هیچ تاریخ canonical متصل نمی‌شود. همین قاعدهٔ
fail-closed برای هر تاریخ مبهم بعدی نیز برقرار است.

### سلامت دهان عملی ۲

در سلامت دهان عملی ۲، هر شماره جلسه یک **جلسهٔ هفتگی واحد** است که برای سه
زیرگروه در شنبه، دوشنبه و چهارشنبه تکرار می‌شود. این سه تاریخ سه جلسهٔ آموزشی
متفاوت محسوب نمی‌شوند. دانشجو در projection شخصی فقط اجرای مربوط به روز خودش
را می‌بیند و بنابراین در هر هفته حداکثر یک بار همان شماره جلسه نمایش داده می‌شود.

روز شخصی سلامت برای روتیشن اول و دوم جداگانه در assignment canonical نگه‌داری
می‌شود (`oralHealthRotationAWeekday` و `oralHealthRotationBWeekday`). ورود هر
فهرست نیز از همان importer و پس از dry-run انجام می‌شود:

```bash
php scripts/import_term7_groups.php --field=oralHealthRotationAWeekday --file=/absolute/oral-health-a.csv
php scripts/import_term7_groups.php --field=oralHealthRotationBWeekday --file=/absolute/oral-health-b.csv
```

اگر روز روتیشن فعال دانشجو ثبت نشده باشد، سلامت برای او حدس زده نمی‌شود. روزهای جبرانی
روتیشن دوم نیز با روز منبع همان برنامه تطبیق داده می‌شوند تا اجرای تکراری برای
زیرگروه نامرتبط ظاهر نشود. تاریخ‌های PDF سلامت عملی و روش تحقیق ۲ مربوط به روتیشن
اول‌اند، اما ترتیب آموزشی این دو درس rotation-relative است: offset هر جلسه نسبت
به شروع روتیشن اول به شروع روتیشن دوم منتقل می‌شود. بنابراین سلامت در هر دو
روتیشن همان هشت جلسهٔ هفتگی را دارد و هر شماره جلسه برای سه اجرای شنبه/دوشنبه/
چهارشنبه یکسان است؛ روش تحقیق ۲ نیز همان توالی جلسه‌های منبع را برای گروه‌های
روتیشن دوم حفظ می‌کند. اگر context روتیشن A/B موجود نباشد، این projection
fail-closed است و از تاریخ مطلق یک روتیشن برای روتیشن دیگر حدس زده نمی‌شود.

طرح درس مبانی اندودانتیکس ۲ که برای نیمسال اول ۱۴۰۵–۱۴۰۶ ثبت شده، صریحاً مربوط به
گردش اول است. چهارده جلسهٔ یکشنبه/سه‌شنبه آن فقط occurrenceهای موجود روتیشن اول را
enrich می‌کنند؛ برای روتیشن دوم عنوان جلسه، کوییز یا استاد از روی الگوی گردش اول
جابجا یا حدس زده نمی‌شود تا منبع صریح روتیشن دوم در دسترس باشد.

مالک سامانه می‌تواند هم‌زمان دانشجوی واقعی باشد. اگر حساب owner شماره دانشجویی
canonical، cohort دقیق `dentistry-1402` و assignment صریح ترم ۷ داشته باشد،
نماهای دانشجویی ClassOps برنامهٔ شخصی همان هویت را نیز نشان می‌دهند؛ owner بودن
نباید projection تحصیلی را حذف کند. owner بدون assignment صریح، برنامهٔ شخصی
ساختگی دریافت نمی‌کند و دسترسی مدیریتی همچنان فقط در مسیر مدیریت ربات باقی
می‌ماند.

یادآوری‌های فردا و رزرو غذا فقط برای اتصال‌های احرازشدهٔ cohort دقیق
`dentistry-1402` ساخته می‌شوند. تأیید رزرو غذا با کلید user canonical + تاریخ
سه‌شنبه ذخیره می‌شود و برای تلگرام و بله مشترک است.
